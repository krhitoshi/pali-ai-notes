# 対訳作成の自動化手順

VRI 版 (Chattha Sangayana Tipitaka) の XML から対訳 md を生成するパイプライン.

```
抽出 (extract_chunks.rb) -> 生成 (claude -p) -> 組み立て (assemble_md.rb)
  -> 検証 (verify_taiyaku.rb)
```

大原則: 原文のバイト列は LLM を一切通さない. 分割・組み立てはスクリプトの
決定論的な文字列操作で行い, orchestrator (このセッション) は原文テキストを
再出力しない. 生成はハーネスの影響を避けるため `claude -p` のクリーンな
別プロセスで行う. Task / subagent での生成は行わない.

設計方針・実装知見の詳細は docs/automation.md を参照する.

## 手順 1: 原文の特定

- 原文は tipitaka.org の VRI XML (例
  `https://www.tipitaka.org/romn/cscd/s0202m.mul0.xml`). URL を渡すと
  `_tmp/` にダウンロードされ, 既に同名ファイルがあればそれを正本として
  再利用する. ローカルの `_tmp/*.xml` を直接指定してもよい
- 対象の経・節は `<p rend="subhead">` の見出しテキストと完全一致で指定する
  (例 `"10. Kimilasuttaṃ"`). どの XML ファイルかは cscd-text MCP の検索や
  既存対訳の Ref を手がかりに特定する
- 註釈書の冒頭部 (序偈など) は `<p rend="subsubhead">` の見出しでも指定
  できる. MN 註の冒頭 (`s0201a.att0.xml`) は `"Ganthārambhakathā"` を指定
  すると, 続く Nidānakathā (構造ブロック strt として出る) を含めてファイル
  末尾までが 1 セクションになる. 出力ファイル名は `mn/mn_attha_000.md`
  (docs/commentary_file_naming.md の「冒頭部の番号」). 対応を確認したのは
  MN 註の冒頭だけで, 他の註釈書・復註の冒頭は構造が異なる (DN 註は
  Nidānakathā の途中に subhead がある等) ため, 段落一覧で範囲を確かめる
- 序偈には VRI 段落番号がない. headings 上書きを付けないと, 後続の
  Nidānakathā の番号を引き継いで全チャンクが `## 1 (N)` になる. 序偈の
  チャンクは headings 上書きで見出しラベルを `0` にする
  (例 `"1:0,2:0,3:0,4:0"`. 見出しは `## 0 (1)` からの連番になる).
  `0` は VRI 段落番号のない冒頭部を指すラベルで, VRI の番号は 1 から
  始まるため実在の番号と重ならない

## 手順 2: チャンク境界と文脈範囲の決定

chunkspec を省略して実行すると段落一覧 (連番, VRI 段落番号, 文字数, 冒頭)
を表示して終了する.

```bash
ruby scripts/extract_chunks.rb _tmp/s0202m.mul0.xml "10. Apaṇṇakasuttaṃ"
```

- chunkspec は bodytext 段落番号 (1 始まり) のグループをカンマ区切りで書く
  (例 `"1,2,3-5,6-11,12,13-15"`)
- 経や註釈の結び行 (MN の "...suttaṃ niṭṭhitaṃ chaṭṭhaṃ.", MN 註の
  "Papañcasūdaniyā majjhimanikāyaṭṭhakathāya" と "...suttavaṇṇanā
  niṭṭhitā." の 2 行など) は段落一覧の末尾に番号なしの行として出る.
  対訳対象なので最終チャンクの範囲に必ず含める (例 最終段落が 29 で結びが
  30-31 なら最終チャンクは `29-31`). 含め忘れると source.txt にはあるのに
  対訳に結びが欠ける (mn_attha_076 で実例あり. issue #16)
- チャンク方針はテキスト種別で異なる:
  - 経典 (mūla. DN/MN/SN など): 1 チャンク 1 VRI 番号が原則. 番号段落と
    それに続く偈行・直前の小見出し (strt) を 1 チャンクにする. 見出しは
    「## 242」の単一番号になる. 番号が文字数目安を超える場合のみ同一番号
    内で分割する (「## 90 (1)」の連番. MN 57 の §81 で実績). 複数番号を
    1 チャンクにまとめる範囲見出しは経典には使わない (DN 31 で誤って適用
    し全体を再生成した実例あり)
  - 原典が偈文だけのものに対する註釈書 (Jātaka-a, Dhp-a など): VRI 番号が
    偈にしか付かず, 物語や語句註は無番号段落になるため, 内容のまとまり
    (現在物語・過去物語・偈+語句註・samodhāna) で複数段落をまとめてよい.
    見出しは headings 上書きで偈の範囲ラベル (「## 115-116 (N)」など) を
    付ける
- 境界と文脈範囲は編集判断のため, 案を作りユーザに提示して確認を得る.
  確認を得るまで生成 (手順 3) に入らない. chunkspec の数字列だけでは
  妥当性を判断できないため, チャンクごとに「チャンク番号 / 段落範囲 /
  見出しラベル / 文字数 / 先頭段落の冒頭」を揃えた一覧を本文で示し, 続けて
  文脈範囲の案 (`TAIYAKU_CTX` を none / all / N のどれにするかと, その
  理由) を 1 行で示してから質問する. 質問は「この境界と文脈範囲でよいか,
  変えたい箇所はどこか」に絞る. 一覧はターン最終のテキストメッセージと
  して送ってターンを終え, 通常の返信で確認を得る. 同一ターンで
  AskUserQuestion を続けて呼ばない (ツール呼び出し直前のテキストは
  表示されないことがあり, 一覧が届かないまま確認だけ求める事故が起きた
  実例あり. 2026/08/04)
- 一覧の「先頭段落の冒頭」は段落一覧の出力 (冒頭 60 字) をそのまま写す.
  原文を読んで内容を要約しない (要約は判断にほとんど効かず, 原文を
  読み込む分だけセッションのトークンを使うため. 2026/11/05)
- 文脈範囲の案の決め方 (仕組みの詳細は手順 3 の `TAIYAKU_CTX` を参照):
  - `all` (セクション全体): AN の vagga のように 1 経が数十字しかない
    (…pe… 省略) チャンクが並ぶとき. 省略元の経や vagga 名が見えないと
    推測で補って誤る (AN 5.187 で実例). セクションが数千字程度なら
    入力の増加は問題にならない
  - `N` (前後 N 段落): セクションが長く (目安 20,000 字超. Vism の章や
    長い註など) 全文を毎チャンクに付けると入力が大きくなるとき.
    N は 2-3 程度から
  - `none` (従来どおり): チャンクが 500 字以上あり前後なしでも読める
    MN の経や註など. 文脈を付けた方が訳の判断材料は増えるが, 既定は当面
    none とし, 比較結果が集まってから既定を見直す
  - 迷う場合は案を none にせず, 候補を 2 つ挙げてユーザに選んでもらう
- 1 チャンクの文字数目安は 500-2,000 字 (2,000 字以上は大きすぎる).
  目安の範囲内では内容のまとまりを優先する
- VRI 番号段落 (`## <番号>` の見出し単位) が目安を超える場合は,
  段落一覧の行境界で複数チャンクに分ける. 見出しは `## <番号> (1)`
  `## <番号> (2)` の連番になる (MN 57 の §81 で実績)
- 分割の最小単位は段落一覧の 1 行 (XML の 1 つの p 要素). 実績では
  1 行の最大は約 2,300 字で目安内に収まっている
- 境界の規則: 各チャンクは「VRI 段落番号付きの段落で始まる」か「直前
  チャンクと同一番号の継続」とする. 1 チャンクに異なる VRI 番号を 2 つ
  含めない (途中から始まる番号がセクション見出しを持てなくなる.
  extract_chunks.rb が該当時に警告を出す)
- セクション一部だけを対訳する場合は `"6-11"` のような途中範囲を指定できる
  (Dhp-a の vatthu で偈と語句註のみ対訳する場合など). 範囲は連続した
  昇順のみ. source.txt は範囲によらず常にセクション全体を正本として書き,
  連結一致 assert は該当範囲 (経題 + 指定段落) との比較になる. 経題行は
  範囲によらず先頭チャンクに含まれるため対訳対象になる
- subhead 起点のセクションは次の見出しで抽出が止まる. セクションの途中に
  内部の小見出しがある場合 (MN 54 註の "Kāmādīnavakathāvaṇṇanā", MN 1 註の
  "Suttanikkhepavaṇṇanā" など) はそこで止まり, 段落一覧が途中までになる.
  段落一覧の末尾に出る「終了位置」で止まった行を確かめる (番号のない
  subhead で止まると「注意」も出る). 内部の小見出しで止まっていれば,
  環境変数 `TAIYAKU_UNTIL` に次のセクションの見出しテキストを指定して
  全体を抽出する

  ```bash
  TAIYAKU_UNTIL="5. Jīvakasuttavaṇṇanā" ruby scripts/extract_chunks.rb \
    _tmp/s0202a.att0.xml "4. Potaliyasuttavaṇṇanā"
  ```

  間にある小見出しと結び行は構造ブロック (strt) として取り込まれ, 対訳
  対象になる. チャンクは小見出しから始めてよく, 小見出しごとの結び行
  ("...vaṇṇanā niṭṭhitā.") は直前のチャンクの末尾に含める.
  `TAIYAKU_UNTIL` は段落一覧の表示と手順 3 のパイプライン実行の両方に
  同じ値を付ける (付け忘れると途中までのセクションで生成される)
- XML ファイル内で最後のセクションは, 後ろに `TAIYAKU_UNTIL` へ指定できる
  見出しがない. 内部の小見出しを持つ場合 (MN 10 註など) は全体を抽出
  できない (未対応の制限. issue #40)

## 手順 3: パイプライン実行

```bash
scripts/taiyaku.sh <xml|url> <subhead> <chunkspec> <workdir> <out_md> \
  <model> [effort] [headings]
```

例:

```bash
scripts/taiyaku.sh https://www.tipitaka.org/romn/cscd/s0202m.mul0.xml \
  "9. Bahuvedanīyasuttaṃ" "1,2,3-5,6-11,12,13-15" _tmp/work_mn059 mn/mn_059.md \
  claude-fable-5-1
```

- model は必須で既定値はない. 呼び出し元セッション (この対訳を作っている
  セッション自身) のモデル ID をそのまま渡す. ID はシステムプロンプトの
  「The exact model ID is ...」に書かれているフル ID (claude-fable-5-1 など)
  を使い, エイリアス (opus 等) は将来別モデルを指すため使わない (taiyaku.sh
  がフル ID 以外を abort する). Opus のセッションなら Opus, Fable なら
  Fable で生成される
- effort の既定値は `high`. 呼び出し元と揃えるなら環境変数 CLAUDE_EFFORT の
  値を渡す
- Meta ブロックのモデルラベルは taiyaku.sh が model と effort から組み立てる
  (claude-fable-5-1 + high -> "Claude Fable 5.1 High"). 手入力しない
- workdir はリポジトリ内 `_tmp/work_...` とする (プロジェクト CLAUDE.md の
  「翻訳の方針」が生成プロンプトに入るのは意図した動作)
- out_md のファイル名にモデル名サフィックス (_fable5 など) は付けない.
  モデル情報は Meta ブロックに入る. 註釈書のファイル名は
  docs/commentary_file_naming.md に従う
- `[headings]` は見出しラベルの上書き指定 `"チャンク番号:ラベル"` の
  カンマ区切り (例 `"1:345-346,4:345-346"`). 番号規則で決まらない編集判断
  (物語導入部や複数偈にまたがる語句註を偈の範囲でラベル付けする等) に使う
- 環境変数 `TAIYAKU_CTX` で各チャンクに前後の原文を参照文脈として付ける
  (issue #23). 値は手順 2 でユーザに確認したものを使い, `none` 以外なら
  `TAIYAKU_CTX=all scripts/taiyaku.sh ...` の形で付けて実行する.
  `all` はセクション全体, 整数 N は前後 N 段落 (段落一覧の行単位),
  未指定 / `none` は従来どおり chunk だけを渡す. 文脈は extract_chunks.rb
  が prompt_NN.txt に「前の文脈 / 訳出対象 / 後の文脈」の順で組み立て,
  訳出対象は chunk_NN.txt と同一. 文脈側は訳出も再掲もさせず, 参照した
  ことを語釈に書くときは経名や段落番号で示す指示を付ける
- 環境変数 `TAIYAKU_JOBS` で生成 (`claude -p`) の同時実行数の上限を指定する.
  既定は 50 で, 通常は指定しない. チャンク数が上限を超える場合は, 空きが
  出るたびに次のチャンクを起動する. 上限を外す目的で大きな値を指定しない.
  チャンク数だけ一度に起動するとマシンが高負荷になる (2026/11/10 に MN 1
  復註の 171 チャンクを同時に起動し, スワップをほぼ使い切った実例あり.
  同日の 76 チャンク同時起動は問題なく完了)
- 生成の認証方法はコマンドで使い分ける. `scripts/taiyaku.sh` は従来どおり
  CLI のログイン (サブスクリプション), `scripts/taiyaku_api.sh` は環境変数
  `PALI_AI_NOTES_CLAUDE_API_KEY` のキーを使った API の従量課金で生成する.
  引数は同じ. `taiyaku_api.sh` は `/taiyaku-api` コマンドで呼ばれたときか
  ユーザが指示したときだけ使う. 中身は
  `TAIYAKU_AUTH=api` を付けて taiyaku.sh を呼ぶだけで, `claude -p` の
  引数はどちらも同じで, 認証だけが変わる (ただし API キー認証では CLI が
  claude.ai コネクタを自動で無効にする)
- workdir には source.txt (read-only の正本), chunk_NN.txt, 生成結果
  out_NN.md, err_NN.log が残る
- taiyaku.sh はセッションの Bash から前面 (フォアグラウンド) で実行し,
  timeout を長めに取る (1 チャンク数分). バックグラウンド (detach) 実行では
  claude -p が exit 0 のまま空出力になる事象があった (2026/07/28.
  同じコマンドの前面実行では成功)

## 手順 4: 生成失敗時の対応

- `API Error: 401` は CLI の OAuth トークン失効. ユーザに `claude login`
  での再ログインを依頼する (再ログイン後はセッション内からの実行も通る)
- `taiyaku_api.sh` での `Invalid API key` はキーが無効,
  `Credit balance is too low` は API のクレジット残高不足. どちらも
  ユーザに対応を依頼する
- 一部チャンクだけ失敗した場合は, そのチャンクのみ taiyaku.sh 内と同じ
  `claude -p` コマンドで再生成すればよい. `taiyaku_api.sh` で生成した
  ものを再生成するときは
  `env -u CLAUDE_CODE_ENTRYPOINT ANTHROPIC_API_KEY="$PALI_AI_NOTES_CLAUDE_API_KEY" claude -p ...`
  の形にする (デスクトップアプリのセッションでは CLAUDE_CODE_ENTRYPOINT を
  外さないとサブスクリプション側で生成される). assemble_md.rb は out がない
  チャンクをスキップして部分組み立てできる (欠けは警告され, verify の
  欠番検査が未生成分を報告する). 長いテキストを数回に分けて生成する
  運用もこの仕組みで行う

## 手順 5: 検証結果の対応

verify_taiyaku.rb は対訳の番号付き行 (パーリ再掲行) を正本と照合する.

- OK / OK-LOOSE / OK-NOSPACE は許容されるドリフト. 対応不要
- NG は要確認. source.txt の該当箇所と比べ, 再掲行を原文の形に戻す.
  実例: 正本にない綴りの標準化 (vutta -> vuttaṃ), 複合語へのハイフン挿入,
  引用符の変形. 全角の “ ” は編集表記でないため " に修正する
  (対訳では VRI の ‘‘ ’’ も用いない. 語句引用は半角 ", アポストロフィは
  半角 '. 再掲行は原文の表記のまま写す)
- NG-SECTION は再掲行が正本全体にはあるが, その `##` セクションの原文
  ブロック (+ 経題) にはない状態. 参照文脈付き生成で文脈側の文を訳出して
  しまった場合に出る. 該当項目を対訳から削除する (訳出対象の項目の通し
  番号が飛ぶ場合は振り直す)
- NG-HEADING は見出しの異常. 許可される見出しは「# 経題」
  「## <段落番号>」「## <段落番号> (連番)」「## <番号>-<番号>」
  「### Meta」「### 対訳」のみ. 生成が作った余計な見出しは削除する
  (経題見出しは番号付き項目へ変換). 欠番はチャンク境界の誤り
  (1 チャンクに複数 VRI 番号) か未生成チャンクを疑う
- md を手直ししたら verify のみ再実行する:

```bash
ruby scripts/verify_taiyaku.rb <workdir>/source.txt <out_md>
```

## 手順 6: 完了確認

- 出力 md をユーザに確認してもらう. コミット・ステージはユーザの明示的な
  指示を待つ
- チャンクごとに独立プロセスで生成するため, 箇条書きの空行や括弧の
  全角/半角など軽微な体裁がチャンク間で揺れることがある. 許容する

## 出力 md の構造

- 先頭に YAML frontmatter (source = 原文 XML の URL, generated = 生成日,
  updated = 最終改訂日. assemble_md.rb が書き, 改訂時は updated を手動更新)
- `# 経題` の下に `## <段落番号>` ごとのセクション. 各セクションは
  原文段落 (正本から byte-exact コピー) -> `### 対訳` -> 番号付き対訳行
- 対訳の通し番号は経題行から始め, 経題・段落番号は番号ごと再掲する
  (`1. 2. Aṭṭhakanāgarasuttaṃ`, `2. 17. Evaṃ me sutaṃ –` の二重番号)
- 末尾に `### Meta` (日付とモデルラベル. assemble_md.rb が書く)
- 生成 system prompt は system_prompt_no_paraphrase.md
